# KM 系统设计文档

**日期：** 2026-03-29  
**主题：** KM（Knowledge + Memory）本地知识库与记忆系统  
**状态：** 已确认，可进入实施计划阶段

---

## 1. 背景

KM 是一个以 **本地 Markdown 文件** 为真相源的个人知识库与记忆系统。

系统目标不是做一个重型笔记软件，而是建立一个可长期演进的本地仓库：

- 用 Markdown 沉淀可复用的技术案例；
- 用 Markdown 维护项目记忆与个人画像；
- 用 Git 管理历史与远程备份；
- 用轻量索引层提升检索体验；
- 用 Codex 插件在需要时执行写入、更新、检索与渐进式披露。

---

## 2. 核心设计原则

### 2.1 本地优先
- 所有核心内容保存在本地文件系统中；
- Markdown 是唯一真相源；
- 索引、缓存、检索结果都可重建，不作为主存储。

### 2.2 Git 管理
- KM 仓库使用 Git 管理版本；
- 支持推送到远程仓库做备份；
- 所有知识演化和记忆更新都应尽量可追踪。

### 2.3 显式触发
- KM 不自动注入到所有新项目上下文；
- 只有在用户明确要求时，系统才执行写入、更新、检索或召回。

### 2.4 渐进式披露
- 检索结果默认返回摘要级信息；
- 只有在用户继续要求时，才展开关键片段、来源路径或完整条目；
- 避免上下文窗口被全量历史内容挤占。

### 2.5 轻量优先
- 第一版不引入向量模型；
- 第一版不以数据库为主存储；
- 第一版优先解决“可持续记录 + 可控检索 + 可追踪演化”。

---

## 3. 内容模型

KM 第一版固定支持三类核心内容。

### 3.1 技术案例（Knowledge）
用于沉淀可复用的技术知识，重点是“问题—方案—适用条件”，而不是机械保存整段代码。

典型内容包括：
- 交互效果实现；
- 优秀代码方案；
- 组件模式；
- 架构解法；
- 踩坑与修复记录。

默认保存内容：
- 解决的问题；
- 实现思路；
- 关键代码片段；
- 来源项目与来源文件；
- 适用场景；
- 限制与坑点。

对于高复用价值的案例，可以额外保存更完整的实现版本。

### 3.2 项目记忆（Memory / Project）
用于维护当前与历史项目的上下文。

典型内容包括：
- 项目目标；
- 当前阶段；
- 技术栈；
- 约束条件；
- 关键决策；
- 当前风险；
- 当前待办。

项目记忆需要支持持续更新，因此既要有当前主档案，也要有变更记录。

### 3.3 个人画像（Memory / Profile）
用于维护用户长期稳定或缓慢变化的画像信息。

典型内容包括：
- 用户身份与角色；
- 正在做的方向；
- 技术偏好；
- 工具偏好；
- UI/交互偏好；
- 工作方式；
- 当前重点项目版图。

个人画像同样应具备主档案与变更记录。

---

## 4. 写入策略

KM 采用 **双层落盘模式**。

### 4.1 正式库
当输入信息足够完整时，系统直接生成正式 Markdown 条目，写入对应正式目录。

### 4.2 Inbox
当输入信息不完整、来源不清楚、需要后续补充时，先写入 `inbox/`，等待后续整理归档。

### 4.3 持续更新型对象
对于项目记忆与个人画像：
- 优先更新正式摘要页；
- 同时追加一条变更记录，保留演化历史。

---

## 5. 检索策略

KM 采用 **轻量方案 C**：Markdown 真相源 + SQLite 索引层 + 混合检索。

### 5.1 索引定位
SQLite 只承担检索职责，不承担主存储职责。

### 5.2 混合检索组成
第一版混合检索包含三层：
1. 结构化字段过滤；
2. SQLite FTS 全文检索；
3. 规则排序。

### 5.3 结构化字段
索引中至少包含：
- 文档 ID；
- 文档类型；
- 标题；
- 摘要；
- 标签；
- 项目名；
- 技术栈；
- 来源路径；
- 更新时间；
- 价值等级或优先级；
- 是否正式条目 / 是否 inbox；
- 关联文档。

### 5.4 规则排序
建议优先级：
- 标题命中 > 摘要命中 > 正文命中；
- 正式条目 > inbox；
- 高价值案例 > 普通条目；
- 最近更新条目可适度加权。

### 5.5 渐进式披露
检索默认输出：
1. 候选标题列表；
2. 每条 1～3 行摘要；
3. 需要时再展开关键代码片段；
4. 最后才回溯完整 Markdown 原文。

---

## 6. 插件职责边界

插件只负责与 KM 交互，不负责成为主存储。

### 6.1 Capture
从自然语言输入中识别用户意图，并自动判断其属于：
- 技术案例；
- 项目记忆；
- 个人画像。

随后完成：
- 信息提炼；
- 落盘路径判断；
- 正式库或 inbox 分流；
- 索引更新。

### 6.2 Update
对项目记忆与个人画像类对象执行增量更新：
- 更新主档案；
- 追加变更记录；
- 刷新索引。

### 6.3 Recall
仅在用户明确要求时执行检索，例如：
- “去 KM 里查一下”；
- “更新我们的 KM”；
- “更新个人画像”；
- “查有没有类似案例”。

### 6.4 Reveal
按照“摘要 → 细节 → 原文”的层次返回信息，避免不必要的上下文膨胀。

## 7. 建议目录结构

```text
KM/
  docs/
    superpowers/
      specs/
      plans/
  inbox/
    captures/
  knowledge/
    cases/
    patterns/
  memory/
    profile/
    projects/
    logs/
  assets/
    images/
    attachments/
  index/
    km.db
  plugins/
    km-memory/
  scripts/
  templates/
```

说明：
- `knowledge/cases/`：正式技术案例；
- `knowledge/patterns/`：可抽象复用的模式；
- `memory/profile/`：个人画像主档案；
- `memory/projects/`：项目主档案；
- `memory/logs/`：项目 / 个人画像变更历史；
- `inbox/captures/`：待整理输入；
- `index/km.db`：SQLite 索引数据库；
- `plugins/km-memory/`：Codex 插件实现；
- `templates/`：各类 Markdown 模板。

---

## 8. 第一版范围

### 8.1 要做
- 初始化 KM 仓库；
- 设计 Markdown frontmatter 与正文模板；
- 建立 SQLite 索引与 FTS 检索；
- 实现显式触发的写入、更新、检索流程；
- 实现渐进式披露输出；
- 提供轻量插件入口。

### 8.2 不做
- 不引入向量模型；
- 不做自动全库注入；
- 不做大规模原始代码复制；
- 不做复杂 Web UI；
- 不做重型同步系统。

---

## 9. 后续扩展位

为了后续平滑升级，第一版应预留：
- `doc_id`；
- `related_docs`；
- `summary`；
- `keywords`；
- 可选 `chunks` 概念。

未来若确有需要，可在不破坏 Markdown 真相源的前提下增量加入：
- 文档切块；
- embedding 字段；
- 语义召回；
- rerank。

---

## 10. 成功标准

第一版完成后，应满足以下标准：
1. 用户可以用自然语言把内容写入 KM；
2. 系统能自动判断是案例、项目记忆还是个人画像；
3. 系统能决定正式入库还是 inbox；
4. 系统能更新 SQLite 索引；
5. 用户可以显式要求检索 KM；
6. 检索结果以渐进式披露返回；
7. 全部核心数据仍然是本地 Markdown，可由 Git 管理与备份。
